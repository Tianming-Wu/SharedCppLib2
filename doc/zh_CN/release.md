# 发版标准

这个库怎么版本化、一次发版包含什么。2026-10 写下；`CHANGELOG.md` 里更早的部分在这套标准之前，
保持原样。

## 更新日志

`CHANGELOG.md` 手写维护。

- **已提交但尚未发布**的改动列在文件顶部的 `### [Unreleased]` 之下。还在工作区里的改动不列 —— 这个
  库是单树开发，条目在提交时写，不提前写。
- 条目沿用旧段落的风格：一条一行，以 `New:` / `Changed:` / `Fixed:` / `Removed:` 开头，点明模块，
  并说明它对使用者意味着什么变化。
- 发版时把 `### [Unreleased]` 这个标题**改名**为它实际成为的版本（`### v3.8.0`）—— 不是复制一份，
  标题本身移动。

## 发版提交

一次发版就是一个提交，里面只有两样东西：

| 文件 | 改什么 |
| --- | --- |
| `CHANGELOG.md` | `### [Unreleased]` 变成版本标题 |
| `CMakeLists.txt` | `project(... VERSION x.y.z)` 里的版本号 |

标题是 `chore: release x.y.z`（**替代了早先的 "bump version"**），不改任何代码，tag（`v3.8.0`，
同一个数字）打在这个提交上。还有东西要修就先单独提交，发版提交不是顺手夹带的地方。

构建与测试要在发版提交**之前**通过，而不是之后。发版提交本身不代表构建：版本号变了不会重新编译
什么，但一个从来没构建过的 tag 是没人能信任的 tag。

## 版本号

`MAJOR.MINOR.PATCH`，按通常的理解：

| | 什么时候递增 |
| --- | --- |
| MAJOR | 破坏了某个不再是早期开发状态的模块的 API 或 ABI |
| MINOR | 新模块、新功能、行为变化 |
| PATCH | 不改变 API 的修复 |

独立模块有自己的 `version:`（写在 `[SCL_STANDALONE_MODULE]` 段里，见
[standalone_module.md](standalone_module.md)），按自己的节奏走 —— 模块的版本和库的版本没有关系。
但模块的变化仍然值得写一条 changelog 条目，因为读库历史的人找的就是这个。

## 不在这套标准里的

- 更新日志之外的发布说明：没有另一份文档需要同步。
- 二进制产物：这个库就是源码，安装前缀是构建输出，不是发布物。
